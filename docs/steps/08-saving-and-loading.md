# Step 8: Saving and Loading the Land Layer

Built 2026-10-20, as step 8 of [the land plan](../plans/land-layer.md). It makes the land layer usable as a whole: `LandMap` generates, saves and loads.

## What it does

- **`LandMap.generate(seed:width:height:cellsDesired:template:elevationLimit:)`** (`Sources/FantasyMapCore/Land/LandMap.swift`) runs the original's pipeline for the land in one call: the grid points from the seed, the cells, the template's heights, the features, then the deep-depression and near-sea lakes. The defaults are the original's (1280 × 800, 10,000 cells, lake elevation limit 20). The recipe records the template, its steps and the settings; the lakes' template option is the template's key, which is what the original holds.
- **`encoded()` and `init(decoding:)`** save and load. Keys are sorted, so the same map gives the same bytes **in the environment this is tested in** (sorted keys are repeatable output, not a universal canonical-JSON guarantee across Foundation versions), and saving a loaded map gives the bytes it was loaded from **for files `encoded()` produced**: a file with no recipe loads with an empty one and so has the field when saved again.
- **What a saved map holds: the exact state** (decided 2026-10-20 after the review of step 7). The seed, the size and the cell count asked for; the cell points and the boundary points; the final heights; **the feature ids, the feature records (including records no cell refers to, such as a lake that was opened into an ocean) and the coast distance**; and the recipe. **Format version 1 and algorithm revision 1** are the first supported (0 was provisional).
- **What loading does:** it validates everything saved, **bounds the work the saved size and cell count imply before any counting loop runs** (the shared `GridPoints.preflight` that generation also uses: a finite positive size and cell count, a usable spacing, and estimated cell and boundary counts within the budget, so a record such as a 1e12 × 1 map with 1e12 cells and one point is refused before anything is enumerated, with the same arithmetic for accepted maps), checks the grid against the saved size, and rebuilds only the cells' neighbours and corners from the points. **It never recomputes the heights, the features, the feature ids, the feature records or the coast distance, and never re-runs the lakes.**
- **What is not saved:** the cells' neighbours and corners (derived, deterministic from the points, and governed by the algorithm revision), and any picture or app state.

## Validation (what a build refuses)

An unsupported format version or algorithm revision; a non-finite or non-positive size or cell count; more points than the budget; different numbers of points, heights, feature ids and coast distances; a height above 100; a non-finite cell point, or one outside the map; a feature table that is empty, whose ids are not 1, 2, 3 ... in order, or in which a record's land flag disagrees with its kind; a feature id that is 0 or not in the table; a cell whose feature is land while its height is below sea level, or the reverse; a coast distance outside -9 ... 1. **The coast distance's sign is deliberately not tied to land or water:** the first round trip of a generated map failed on this, because the original itself leaves a positive distance on a water cell beside a depression lake (its shore marking reaches a neighbouring water cell), so the original's own state is valid. When loading a map, the number of cell points and the **boundary points must be the ones the size and cell count give** (so a corrupt file, or an algorithm that changed under the same revision, is refused rather than silently read differently). Decoding validates, so a refused map never loads half-formed.

**Resource policy is separate from format compatibility.** A build may refuse a file that exceeds its own limits (the point budget, the preflight's estimate), including a file another build could generate; that is not a format error. Reducing the budget in a later build is a compatibility decision to be made deliberately, not a side effect. Not detected: a cell point moved slightly inside the map without changing anything else, since the file has no checksum. **No checksum is planned for this first format:** validation says whether state is acceptable, not whether it was edited. **Compatibility discipline:** any change that alters the rebuilt cells must change the algorithm revision or keep the old rebuild; fixtures saved at revision 1 should be kept and their rebuilt geometry compared in future changes (a digest of the cells in the file would help against a missed bump and is optional, not done). **Fixed revision-1 fixtures** (`Tests/FantasyMapCoreTests/Fixtures/revision1`, three saved maps and a manifest) now guard this: they are committed once and never regenerated by a test, so a change that alters the rebuilt cells, the format or the loaded state fails even if generating and loading changed alike. Each carries an opened lake's retained record and coast state a fresh marking would not give. The manifest holds, per file, the digest of its bytes, of its heights and feature ids, and of the cells and vertex coordinates rebuilt from it; **for all three the expected cell digest is also the original's own** (their grids are ones the original's `Grid.generate` was captured for). They can be rewritten only deliberately, by `MAP_WRITE_REVISION1=<folder> swift test --filter RevisionOneFixtureTests/writeTheFixtures`, with a revision bump explained in the commit.

## How it is tested

- **350 maps** (all 14 templates on five grids at five elevation limits, the default map excluded, tested separately): `LandMap.generate` gives the **original's own state after the lakes** (digests of the heights, the coast distance and the feature ids, and the feature records, from the lake fixtures, so the whole pipeline in one call equals the original's), and every map **round-trips exactly**: the loaded map equals the generated one, the **rebuilt cells equal the generated map's cells**, and saving the loaded map gives the same bytes. Among them, many carry state a fresh marking of the features would not give, and many carry the retained record of an opened lake, and all of these load exactly.
- **The default map** (1280 × 800, 10,000 cells, `highIsland`) matches the original and round-trips.
- **Loading never runs the lakes again:** a map made with the elevation limit 80 (no depression lakes) loads without them, while the same map at the default limit has more.
- **Determinism:** the same inputs give the same bytes; another seed does not.
- **Excessive work is refused before enumeration:** six size and cell-count combinations that imply a trillion columns, far too many points, an area that overflows or underflows, a spacing of zero, and a strip with no room for a point, each given to a one-cell record, are refused with `gridDoesNotMatchSize`, and the shared preflight itself refuses each. **The assertion is deterministic, not a stopwatch:** the preflight runs before either counting loop and before the boundary is built, so the rejection precedes any enumeration (a wall-clock assertion could fail on a busy machine and cannot interrupt a call that hangs). The shared preflight is the one generation uses.
- **Refusals:** a file whose boundary points, cell count or width disagree with its size is refused with `gridDoesNotMatchSize`, and corrupt content (a missing height, a feature id outside the table, an unsupported version, not JSON) fails decoding. The saved record's validation has its own tests for every rule above.
- The same 97 tests pass in a release build (one of them, the deliberate fixture writer, is skipped in a normal run).

## Measurements (one run each on the machine this was built on; not a benchmark, not a promise)

| | cells asked | file size | generate | save | load |
|---|---|---|---|---|---|
| release | 10,000 (9,954 made) | 231 KB | 13 ms | 5 ms | 16 ms |
| debug | 10,000 | 231 KB | 177 ms | 5 ms | 100 ms |
| release | 100,000 | 2.28 MB | 0.36 s | 46 ms | 0.17 s |
| debug | 100,000 | 2.28 MB | 3.2 s | 45 ms | 1.07 s |

The file holds the cell points, the boundary points, and the heights, feature ids and coast distance for each cell as readable JSON arrays. A packed binary form would be smaller and was not tried.

## What it does not show

The land layer is complete for the features the plan set, at the dependency versions in `Fixtures/original/provenance.json`; parity is for the captured maps. Climate, rivers, biomes, realms and drawing are later layers and are not built. Cancellation and a grid-size-aware work budget are follow-up work before an app exposes editable scripts.
