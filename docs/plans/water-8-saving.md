# Plan: Saving and loading the exact water state (water stage 8)

Status: plan, one-file decision taken 2026-10-21; built 2026-10-21 ([step page](../steps/water-8-saving-and-loading.md)). Design phase: **what is saved and what loading promises, not how it is coded.** Nothing here is built. It follows [the water plan](water.md) (stages 1 to 7 are done) and the land layer's [step 8](../steps/08-saving-and-loading.md), whose rules it keeps: the exact state is saved, loading recomputes nothing, loading never re-runs a generation step, and loading validates and bounds its work before it enumerates anything.

## What it promises

A water map loaded from a file is **identical** to the one saved: the same arrays, records and lake fields, and saving it again gives the same bytes (in the tested environment, as for the land). Loading does not run the temperature, the rain, the packed graph, the features, the lakes or the rivers again: the stored climate, heights, river records and lake fields are kept without regeneration.

**What that does not promise.** Some things are derived from the current code and not stored: the cells' topology is rebuilt with the current geometry implementation, the coordinate and area checks use current calculations, and the meandered points will be regenerated for drawing. Compatibility therefore needs revision-specific behaviour, or an explicit refusal, when one of those derived algorithms changes. The fixed files and their topology digests are good safeguards and not a universal guarantee; equal areas do not prove identical topology, and consistent edits are not detected as corruption (there is no checksum). Byte-identical resaving is a claim for the tested environment.

## What is saved (the final state)

| Part | Saved | Why |
|---|---|---|
| Land map | the whole land map as the land layer saves it | the water chain starts from it and nothing else holds the grid |
| Geography | the request and the result (map size, latitude, longitude, the latitude and longitude box) | the temperature and the rain read it; the random draws that made it are not repeated |
| Settings | temperature, precipitation (rain level, winds), river settings, the cell count asked for | so the map says how it was made; **one height exponent**, as the review asked |
| Grid climate | temperature (`Int8`) and rain (`UInt8`) per grid cell | the lake climate and the rivers read them |
| Packed graph | the points, each cell's grid cell, the **final** heights (after the erosion) and the areas | the packed cells' neighbours and corners are derived from the points |
| Packed features | feature number, distance field, haven and harbour per cell; the feature table with rings, shorelines, heights and **the final lake fields** (flux, temperature, evaporation, and the inlets and outlet that name surviving rivers) | the table is the lakes' record |
| Rivers | flux, river number and confluence flux per cell; the river records (cells, source, mouth, discharge, length, width, width factor, source width, parent) | the rivers' final state |

## What is not saved

- The **temporary lake fields** the original deletes in `cleanupLakeData` (`river`, `enteringFlux`, `outCell`, `closed`), the working heights before the erosion, the random state (each stage resets it from the seed), the work report, and the meandered points (temporary; the records keep cells and scalar dimensions, so a drawing that needs the points regenerates them from the cells deterministically).
- The packed cells' neighbours and corners: derived from the points and governed by the algorithm revision, as for the land layer.
- Any picture or app state.

## What loading refuses

Everything the generator's own structural validation refuses (arrays that do not fit one another, a cell without 1 to 20 neighbours, feature numbers outside the table, water in land features and the reverse, a haven that is not a neighbouring water cell, a lake without its shore), plus: river numbers outside the records, river cells outside the map, a river with fewer than three cells, a parent that is not a record, a lake's inlet or outlet that is not a record, non-finite numbers, and sizes whose preflight exceeds the budget. A refused file never loads half-formed. Resource limits stay separate from format compatibility, as in the land layer.

## Versions

A format version and an algorithm revision, as the land layer has, starting at 1. **Fixed fixtures** saved at the first revision are committed once and never regenerated by a test, so a change to the format or to the rebuilt cells fails even if generating and loading changed alike. The land file's own version is unchanged; the water file embeds it.

## How it would be tested (what, not how)

Round trips on many generated maps (all the fixture runs' kinds: lakes with inlets and outlets, rivers leaving by the border, erosion on and off); equality of the loaded map's every part with the saved one; the same bytes on a second save; a loaded map equals one generated again from the same inputs; each refusal above has a test; mutation checks as before; file size and times at 10,000 and 100,000 cells reported as measurements.

## Not in this stage

Biomes, drawing the water, a binary format, reading the original's `.map` files and any app change.

## Decided

1. **One file** (the author, 2026-10-21): the land map and the water state are saved together, so a water map cannot be loaded against the wrong land map. A separate water file naming a land map by a digest was set aside.
